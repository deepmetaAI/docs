# 错误码

Cloubic API 在请求失败时会返回 HTTP 状态码和错误信息。接入时建议优先根据 HTTP 状态码判断错误大类，再结合响应中的 `message`、`type`、`code` 和 `request_id` 排查具体原因。{{ className: 'lead' }}

<Note>
  本页列出的是通用错误处理方式和常见错误类型。不同模型或上游服务返回的 `code` 可能存在差异，请以接口实际响应为准。
</Note>

## HTTP 状态码

| 状态码 | 含义 | 常见原因 | 处理建议 |
| --- | --- | --- | --- |
| `400` | 请求格式或参数错误 | JSON 无效、缺少必填参数、参数类型不正确、上下文长度超限 | 修正请求体；检查模型支持的参数、消息格式和 token 长度 |
| `401` | 认证失败 | API Key 缺失、格式错误、已删除、未生效 | 检查 `Authorization: Bearer YOUR_API_KEY`；重新生成密钥 |
| `403` | 权限不足 | 账户或密钥无权访问该模型、端点或组织资源 | 检查模型权限、账户状态、密钥权限范围 |
| `404` | 资源不存在 | 路径错误、模型 ID 不存在、任务 ID 不存在 | 检查接口路径、模型名称和资源 ID 是否正确 |
| `429` | 频率或额度限制 | 请求过于频繁、并发过高、余额不足、模型限流 | 降低并发；使用指数退避；检查余额和套餐限制 |
| `500` | 平台内部错误 | 平台服务异常或未知错误 | 记录 `request_id` 后重试；持续失败时联系支持 |
| `502` | 上游服务错误 | 模型供应商异常、网关连接失败 | 短暂退避后重试；必要时切换模型 |
| `503` | 服务暂不可用 | 模型维护、上游拥塞、平台限流保护 | 延迟重试；降低并发；关注控制台状态提示 |
| `504` | 网关超时 | 上游模型处理超时或网络链路超时 | 缩短输入、降低生成长度、使用流式输出或稍后重试 |

<Note>
  `4xx` 通常表示请求、认证、权限或额度问题，直接重试一般不会成功。`429` 和 `5xx` 可能是临时问题，可按退避策略重试。
</Note>

## 常见错误类型

以下错误码是接入时最常见的类型，用于说明处理方式。实际返回值可能因接口、模型或上游服务不同而变化。

| 错误类型 | 常见状态码 | 说明 | 排查方式 |
| --- | --- | --- | --- |
| 认证失败 | `401` | API Key 缺失、无效或格式错误 | 检查 `Authorization` 请求头，确认密钥未复制错误 |
| 权限不足 | `403` | 当前账户或密钥无法访问目标模型或资源 | 检查账户状态、模型权限和密钥权限 |
| 参数错误 | `400` | 请求体格式、参数类型或取值不符合要求 | 查看 `message` 和 `param`，按接口文档修正请求 |
| 模型不存在 | `404` | 模型 ID 写错或当前不可用 | 在模型广场确认模型名称和可用端点 |
| 上下文超限 | `400` | 输入内容和最大输出长度超过模型限制 | 缩短消息历史，降低 `max_tokens` |
| 额度或频率限制 | `429` | 余额不足、QPS 过高、并发过高或触发模型限流 | 检查余额和限额，降低并发并退避重试 |
| 上游服务异常 | `502` / `503` / `504` | 模型供应商异常、超时或临时不可用 | 稍后重试，必要时切换备选模型 |

## 流式接口错误

流式接口可能在建立连接前返回普通 JSON 错误，也可能在连接建立后中断。客户端需要同时处理这两种情况。

<Row>
  <Col>
    ### 建立连接前失败

    如果鉴权、参数校验或额度检查在开始生成前失败，响应通常不是 `text/event-stream`，而是普通 JSON 错误。此时应按非流式错误处理。

    ### 生成过程中失败

    如果连接已经建立，上游模型在生成过程中异常中断，连接可能被关闭，或者收到包含错误信息的数据块。客户端应保存已收到的内容，并将本次结果标记为未完整完成。
  </Col>
  <Col sticky>
    <CodeGroup title="流式错误示例">

```text {{ title: 'SSE' }}
data: {"id":"chatcmpl_123","object":"chat.completion.chunk","choices":[{"delta":{"content":"前半段内容"}}]}

data: {"error":{"message":"The upstream provider timed out.","type":"server_error","code":"server_error"},"request_id":"req_01JZ2Q7XK4Z8H9Y3R5T6N2P1AA"}
```

    </CodeGroup>
  </Col>
</Row>

## 重试策略

建议仅对可恢复错误进行自动重试，并设置最大重试次数。对参数错误、认证失败、权限不足等确定性错误，直接重试通常不会成功。

| 场景 | 是否建议重试 | 建议策略 |
| --- | --- | --- |
| `429`、`500`、`502`、`503`、`504` | 是 | 指数退避重试，加入随机抖动，最多 `2-3` 次 |
| `400`、`401`、`403`、`404` | 否 | 修正请求、权限、资源或业务配置后再发起新请求 |
| 流式连接中断 | 视业务而定 | 如果请求具备幂等性，可重新发起；否则提示用户重新生成 |

```javascript {{ title: 'Node.js 简单重试示例' }}
async function requestWithRetry(sendRequest, maxRetries = 3) {
  let lastError

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await sendRequest()
    } catch (error) {
      lastError = error

      const status = error.response?.status
      const retryable = [429, 500, 502, 503, 504].includes(status)
      if (!retryable || attempt === maxRetries) {
        throw error
      }

      const retryAfter = Number(error.response?.headers?.['retry-after'])
      const backoff = retryAfter
        ? retryAfter * 1000
        : Math.min(1000 * 2 ** attempt, 8000)
      const jitter = Math.floor(Math.random() * 300)

      await new Promise((resolve) => setTimeout(resolve, backoff + jitter))
    }
  }

  throw lastError
}
```

<Note>
  对会产生副作用的接口，建议在业务侧使用幂等键或请求去重机制，避免网络超时后重复提交导致重复扣费或重复创建资源。
</Note>

## 排查清单

1. 确认 `base_url` 是否为 `https://api.cloubic.com/v1`，接口路径是否正确。
2. 确认请求头包含 `Authorization: Bearer YOUR_API_KEY`，并且密钥来自当前账户或组织。
3. 在模型广场确认模型 ID、可用端点、上下文长度、输入类型和输出能力。
4. 检查请求 JSON 是否合法，`Content-Type` 是否为 `application/json`。
5. 对 `429` 错误，检查余额、套餐额度、QPS、并发和 token 速率限制。
6. 对 `5xx` 错误，记录 `request_id`，使用退避策略重试，并准备备选模型。
7. 对流式中断，记录已接收内容、最后一个数据块、断开时间和 `request_id`。

## 联系支持时提供的信息

为了更快定位问题，建议提供以下信息：

- `request_id` 或响应头中的 `x-request-id`
- HTTP 状态码与 `error.code`
- 接口路径，例如 `/v1/chat/completions`
- 模型 ID、请求时间、所在时区
- 是否为流式请求，以及连接断开前是否收到部分内容
- 可脱敏的请求体和响应体
- 客户端 SDK、运行语言和版本
